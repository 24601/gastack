gstack-gastown bridge

Less toil between
design and deploy.

The bridge connects gstack's design pipeline to gastown's agent execution. It doesn't replace your judgment — it removes the manual translation work between them so you can focus on taste and decisions instead of toil.

PLAN — extract tasks from design doc (regex + LLM)
  ↓
EXECUTE — gt convoy create + gt sling per task → agents work
  ↓
REVIEW — claude -p /review + claude -p /cso in parallel
  ↓
  quality.ts → PASS / WARN / BLOCKED
  ↓
REFINE — you approve / reject / retry (scoped signals)
  ↓
DEPLOY — gt convoy land → merge queue
  ↓
DONE
Six stages. One event log. Crash → restart → resume where you left off.

You're still the wisdom in the loop. The bridge reduces toil, not judgment. Mapping gstack's design pipeline to gastown's execution layer is not trivial — the bridge encodes awareness of both stacks so the interfacing is done right. gstack's quality standards flow into dispatch decisions. gastown's execution reality flows back into review gates. The non-trivial part is making them more together. Your time goes to taste and decisions, not the mechanical translation between tools.

What the bridge handles for you

The gap between where gstack leaves off (reviewed design) and where it picks up again (code review) is full of mechanical work. That's what the bridge automates.

The toil (without bridge)

  • Read design doc, extract tasks manually
  • Create work items in gastown
  • Dispatch to agents one by one
  • Poll for completion
  • Run /review manually
  • Run /cso manually
  • Interpret findings, decide next step
  • Trigger merge manually

Mechanical. Repetitive. Easy to shortcut.

What stays with you

  • Reviewing the design before it ships
  • Approving or rejecting quality findings
  • Overriding security gates with reason
  • Deciding when to retry vs. ship
  • Watching the event stream if you want
  • Setting quality policy thresholds
  • Tuning which reviews matter
  • Choosing when to run the pipeline

Taste. Judgment. Final say.

How it works

The interesting part of the bridge isn't connecting two CLIs — it's doing so reliably while keeping you in control.

Event log is the state Zero mutable fields. Everything derived from append-only JSONL. Crash → replay log → reconstruct stage, tasks, pending approvals.
Idempotency tokens SHA-256 of (adapter, command, args). Written to log before result processing. No duplicate dispatches or reviews on restart.
Scoped approval signals Your decisions carry {runId, stage, reviewCycle}. Stale approvals from previous review cycles are ignored. Your latest judgment is always what counts.
Fail closed on parsing gt --json returns non-JSON → BLOCKED and surfaced to you. Never falls back to text scraping. All CLI calls via Bun.spawn with array args.
Quality gates encode both stacks gstack's /review and /cso run in parallel. gastown's execution results feed back. The policy reflects what both tools consider important.
Adaptive output 3×3 grid: detail × style. Verbose on your first run, minimal by run 10. --verbose/--quiet override. It learns how you work.

Quick start

Requires gstack and gastown installed independently. Both CLIs on PATH. The bridge inherits their credentials from your shell environment.

# Install (requires Bun v1.0+)
$ bun install && bun run build
# Start the design-to-deploy pipeline
$ bridge start --design-doc ~/.gstack/projects/my-design.md --rig myproject
# Watch the event stream (optional — the bridge notifies you when needed)
$ bridge watch <run-id>
# When the quality gate blocks, it's your call
$ bridge approve <run-id> --stage REVIEW --cycle 1 --reason "accepted risk"
